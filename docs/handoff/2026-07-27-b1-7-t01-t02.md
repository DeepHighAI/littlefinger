## Decisions made

**1. Two endpoints, atomic composition** (PO, 2026-07-27). `promise-create` takes `send`;
`send: true` makes `lf_promise_create` call `lf_invite_issue_row` inside the same transaction.
`promise-invite` exists separately because §4-3-2 resend needs it. A test asserts that a failure in
the invite step leaves **no** promise row — that property is the whole reason the composition is
server-side.

**2. T-02 returns the token, not the URL** (PO, 2026-07-27). The client assembles
`https://{web}/i/{token}` from `WEB_BASE_URL`. C-3 is still open, so the domain stays out of the
server.

**3. EC-H05 counts by KST calendar day.** Settled from the spec, not asked: EC-H05's user-facing
string is "오늘은 더 만들 수 없습니다. **내일** 다시 시도해 주세요." A rolling 24h window makes that
sentence false.

**4. T-02 writes no `approvals` row.** Also settled from the spec. §7-1 T-02's "예약 기록" means
*reserved*: §4-3-5 step 5 writes **two** rows at approval time, and `approvals.content_hash` is the
confirmed hash, which does not exist before ACTIVE. `lf_promise_approve` already does this correctly
with `i.created_at` as the creator's `acted_at` — **no companion change was needed.** The kickoff
called this "the single most likely integration bug"; it was not a bug. A test asserts 0 approval
rows after T-02.

**5. Client write path revoked** (PO, 2026-07-27). Dropped `promises insert own draft`,
`promises update own draft`, `promise versions insert own draft`. With them open, EC-H05's limits
were bypassable (only the RPC counts) and `content_hash` was client-settable, which J-09 assumes it
is not. `promise_participants` never had an INSERT policy, so those policies could only ever produce
a half-built promise. **`promises delete own draft` is kept** (§4-2-2.5).

## Two things worth not rediscovering

**The idempotency/token trap.** The raw token exists in exactly one response and is never
recoverable. On an idempotent retry the RPC returns the *first* call's cached payload — so if the
shell attached the token it just generated, the user would get a link whose hash is not in the DB,
and the only symptom would be `E_NOT_FOUND`. Fix: the RPC returns `token_hash`; `attachToken()`
includes the plaintext **only when that hash matches the one it just computed**, and always strips
`token_hash` from the client response. The contract ("no `token` means this is a cached replay —
use the first response's token") is documented on `PromiseInviteResponse`.

**The end-date guard is status-dependent, deliberately.** DRAFT → PENDING applies §7-1 T-02's
"종료일 미경과". A **resend while PENDING does not.** If it did, the combination *expired invite +
passed end date* would trap the promise in PENDING forever: the creator cannot edit a PENDING
promise, and EC-B10's only exit is the partner's 수정 제안 (T-05), which needs a working link. Same
reasoning that kept the end-date guard off decline/amend (0007). Rule of thumb it encodes: guard only
when the actor can act on the failure.

## Blocked — the one kickoff item not done

**"Walk a real invite end to end" could not be run.** It needs a real Kakao JWT, which needs a
surface that issues one: SCR-A03 (`apps/mobile` has only SCR-A01) or the acceptance web
(`apps/web` does not exist). The `service_role` key is deliberately not in the local `.env`
(CLAUDE.md §9), so a session cannot mint a user either.

Consequence: **`promise-approve`'s happy path is still PGlite-only on the live project**, exactly as
the kickoff described. That does not change with T-01/T-02 built — it changes when a login surface
exists. The pepper contract itself *is* now covered: `promise-create-invite.test.ts` issues a token
and resolves it through `lf_invite_resolve`, and two mutation tests confirm a wrong/absent pepper
fails, so the test is not vacuous.

## Not in scope, deliberately

- **DRAFT 수정** (§4-2-2.4, overwrite v1). Closed by the RLS revoke; needs its own RPC. No screen
  exists for it yet, so nothing regressed.
- **링크 무효화** (S-11, revoke only, promise stays PENDING) and **증인 초대** (F-05). Both reuse the
  same token machinery — `lf_invite_issue_row` filters `target_role = 'PARTNER'` in every query so
  witness invites can be added without disturbing partner invites. A test asserts a WITNESS row
  survives a partner resend.
- **`daily_metrics.invite_sent_count`.** Left at 0 on purpose. §4-3 never asks for it, and the
  paired `invite_accepted_count` is not incremented by the approve path — filling one inline and not
  the other would make the two columns mean different things. J-07 should compute both from source.

## The exact next step

Backend for M1's first half is now continuous from creation to confirmation *in SQL*, but nothing
can drive it. Two candidates:

1. **`apps/web` (SCR-W01 → W02 → W03)** — this is what makes the end-to-end walk possible at all,
   and it is the surface with no login-wall friction. It reuses `design-reference` CSS verbatim.
2. **SCR-A03 (약속 작성) in `apps/mobile`** — the producer side; needs the components after SCR-A01.

Recommend **1**, because it is the only one that unblocks the verification debt above: with the
acceptance web live, a token issued by `promise-invite` can be pasted into a browser and walked
through Kakao login → approve, which exercises `promise-approve`'s happy path, `content_hash`
generation, the NT-01 notification insert, and the reminder schedule — none of which has ever run
outside PGlite.
