# Kickoff — B1-7: T-01 (약속 생성) + T-02 (초대 발송)

## Why these two together

The user asked for T-02. T-02 alone cannot be exercised: it transitions `DRAFT → PENDING`, and
nothing creates a `DRAFT`. **T-01 and T-02 are one unit of work.**

What they unlock, which is the actual point:

- **No transition has ever succeeded on the live project.** Every live call so far has been a failure
  path. The happy paths of `promise-approve` / `-decline` / `-amend` — the notification insert, the
  `dedupe_key` shape, `content_hash` generation, the reminder schedules — remain PGlite-only.
- **The pepper contract has only one side built.** `invite-resolve` hashes a token to look it up.
  Nothing issues one yet. T-02 is the issuing side.
- **Kakao login has never completed a round trip.** A real invite link is what makes SCR-W01 → login
  → SCR-W02 walkable.

## The one thing that will silently destroy everything

**T-02 must hash the token with `inviteTokenHash` — `SHA-256(token + INVITE_TOKEN_PEPPER)`.**

`supabase/functions/_shared/hash.ts` already holds it and `invite-resolve` already uses it. If the
issuing path computes the hash any other way — different pepper, different concatenation order,
pepper omitted, hashing after URL-encoding rather than before — then **every valid link fails as
`E_NOT_FOUND` and there is no other symptom.** No error, no log, nothing to trace. The token is never
stored in plaintext, so there is no way to diagnose it after the fact either.

Write the cross-path test first: issue a token, resolve it, assert it resolves. Then mutate the
issuing hash and confirm the test fails.

`INVITE_TOKEN_PEPPER` and `PII_HASH_SALT` are registered in Supabase Secrets (verified live).

## Where the token itself may exist

`02` §4-3-1: 32 bytes CSPRNG → URL-safe Base64, **DB stores the hash only**, the plaintext lives in
the link. §13 makes that an acceptance item: "초대 토큰 원문이 DB·**로그** 어디에도 저장되지 않는다".

So the raw token is returned in the T-02 **response body once** and never again. It must not reach
`console.error`, must not go into `approvals`, must not appear in any RPC argument. The RPC receives
the hash; the Edge Function generates the token and does the hashing — same split as
`invite-resolve`.

## T-01 — `— → DRAFT` (`02` §4-2-2, §5-1)

Side effects (`02` §7-1 T-01 + §4-2-2):

1. `promises` 1 row + `promise_versions` 1 row (`version_no = 1`). **The original is
   `promise_versions`**; the same columns on `promises` are a list/batch cache.
2. `content_hash` computed now via `lf_content_hash`, but the legally meaningful hash is the one at
   ACTIVE (F-04). `promise_versions.content_hash` is NOT NULL, so this is forced anyway.
3. `promise_participants` 1 row, `CREATOR`, `status = JOINED`.
4. DRAFT edits **overwrite version 1** — `version_no` does not increment (pre-ACTIVE, so P3 does not
   apply). That is a separate transition to build later, not part of T-01.
5. DRAFT delete is creator-only, hard delete. Also later.
6. **EC-H05 abuse limits: 20 concurrent DRAFTs per user, 30 new promises per day → `E_RATE_LIMIT`.**
   `DRAFT_MAX_CONCURRENT` and `PROMISE_MAX_PER_DAY` already exist in `packages/shared/src/config.ts`;
   SQL cannot import it, so cross-check them in the test the way `rate-limit.test.ts` does.

Field rules are `02` §5-1, and `packages/shared/src/validation.ts` already implements every one of
them as pure functions. **The RPC must re-validate anyway** — §2-3 says server validation is final and
the RPC cannot assume its input came through the client path. That is the same reasoning that produced
`lf_normalize_input`.

| # | key | required | rule |

| 1 | `title` | ✅ | 2–40 codepoints, no newline |
| 2 | `body` | ✅ | 5–1000, newlines allowed, max 20 lines |

| 7 | `penalty` | — | 0–100 |
| 8 | `witness_enabled` | — | boolean, default false |

**`validateEndDate(value, now)` takes the instant as an argument.** Keep that property — the RPC
re-runs the identical rule server-side rather than trusting a client-computed date.

## T-02 — `DRAFT → PENDING` (`02` §7-1, §4-3-1, §4-3-2)

Preconditions: every `02` §5-1 required field valid, **end date not passed**.

Side effects:

1. Conditional `UPDATE promises SET status='PENDING' WHERE id=? AND status='DRAFT'` — 0 rows →
   `E_STATE_CONFLICT` (§7-3.1).
2. `invitations` row: `target_role='PARTNER'`, `token_hash`, `created_by`, `expires_at = now() +
   INVITE_TTL_HOURS (72)`, `status='PENDING'`.
3. **`approvals` row for the creator, action `APPROVE`.** `02` §4-3-6 is explicit: 초대 발송 = 작성자의
   승인 의사 표시. There is no second creator approval at confirmation time. `lf_promise_approve`
   already writes this row itself at T-03 using `i.created_at` as `acted_at` — **check whether that
   double-writes once T-02 also writes one.** This is the single most likely integration bug.
4. `reminder_schedules` row, kind `INVITE_EXPIRE_SOON`, `fire_at = expires_at - 12h` (§8-2).
5. Resend (§4-3-1): new token issued, **existing token immediately `REVOKED`**, `resend_count + 1`,
   `parent_invitation_id` chained. **EC-B08: max `INVITE_RESEND_MAX` (10) per promise →
   `E_RATE_LIMIT`.**

Not part of T-02: 링크 무효화 (S-11, revoke only, promise stays PENDING) and witness invites (F-05).
Both reuse the same token machinery — write it so they can.

## Conventions this must follow

- **Migrations are append-only for real now.** `db push` has run; 0001–0008 are applied. Start at
  **0009**. Editing an applied file is no longer possible (B1-6 used that window once, D-v).
- **The transition is a Postgres `lf_*` function; the Edge Function is a shell** (ADR 0003). Guards,
  locks, writes and the response payload go in SQL. The shell does JWT → user id, request shape,
  RPC call, error mapping, and post-commit notification.
- **`handler.ts` (pure, takes `Deps`) + `index.ts` (`Deno.serve` only).** Not style — a Deno global at
  module top level makes the file unimportable by Vitest.
- **Server-only functions need the three-way revoke** — `from public, anon, authenticated`, granted
  only to `service_role`, asserted per function with `has_function_privilege`. Verified live: this is
  what produces `42501` for `anon`.
- Relative imports carry `.ts`. Korean comments explaining **why**. `npm test && npm run typecheck &&
  npm run check:agents` before commit — and check exit codes, do not read a pipeline's tail.
- **Never run `supabase config push`** (CLAUDE.md §3).

## Decisions the PO will have to make

1. **Does T-01 create-and-send in one call, or two?** §4-2-1's primary CTA is [상대에게 보내기], which
   creates the DRAFT *and* sends in one user action, while [임시저장] only creates. Two RPCs composed by
   the client is simpler but makes the common path non-atomic — a crash between them leaves an orphan
   DRAFT. A single `lf_promise_create_and_invite` keeps it atomic but duplicates T-02's body.
   Recommendation: two RPCs, and one shell endpoint that calls both **inside one RPC wrapper** so the
   transaction boundary still covers both.
2. **What does T-02 return?** The raw token is needed to build the link, and `EXPO_PUBLIC_WEB_BASE_URL`
   is client-side config. Does the server return the token only, or the assembled
   `https://{web}/i/{token}` URL? Returning the URL puts the domain in the server, which C-3 has not
   settled.
3. **EC-H05's two limits need a counting rule.** "일일 신규 약속 생성 30건" — by KST calendar day, or a
   rolling 24h? `rate_limit_counters` uses fixed windows; `daily_metrics` uses KST calendar dates.
   Recommendation: KST calendar day, consistent with `daily_metrics` and §2-2.
4. **Does the creator's `approvals` row belong to T-02 or T-03?** See side effect 3 above — the answer
   determines whether `lf_promise_approve` needs a companion change, which is now a new migration.
