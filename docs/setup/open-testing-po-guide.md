## 1. 광고 ID 선언 — 차단 요인

**경로** Play Console → 리틀핑거 → 왼쪽 메뉴 **모니터링 및 개선 → 정책 및 프로그램 → 앱 콘텐츠** →
**주의 필요(1개)** 탭 → **광고 ID** → **선언 시작**.

**입력값**

| 질문 | 답 |
|---|---|
| 앱에서 광고 ID를 사용하나요? | **예** — `react-native-google-mobile-ads`(AdMob)가 매니페스트에 `com.google.android.gms.permission.AD_ID`를 넣는다 |
| 광고 ID 사용 목적 | **광고 또는 마케팅**만 체크. 분석·앱 기능·사기 방지·개인 맞춤 설정·개발자 커뮤니케이션은 체크하지 않는다 |
| 정책 준수 확인 체크박스 | 체크 |

**저장** 후 **데이터 보안**과 어긋나지 않는지 본다: 앱 콘텐츠 → 조치됨 → 데이터 보안 → 관리 →
"기기 또는 기타 ID" 가 **수집됨 + 공유됨(광고 또는 마케팅)** 인지. 답이 다르면
`docs/setup/play-data-safety.md` 기준으로 데이터 보안을 고친다(광고 ID 선언이 아니라).

**확인** 앱 콘텐츠 상단 탭이 **주의 필요(0개)** 로 바뀐다.

## 4. Google OAuth 동의 화면 — 프로덕션 전환(완료) + 브랜드 인증

**2026-09-03 확인: 게시 상태는 이미 "프로덕션 단계"다.** "앱 게시"는 적용됐고, 스코프가
`openid`·`userinfo.email`·`userinfo.profile` 세 개(비민감)뿐이라 데이터 액세스 인증은 필요
없다(인증 센터 두 번째 카드가 그렇게 말한다). 누구나 Google 계정으로 로그인할 수 있으므로
**§4의 차단 요인은 해소됐다.** 콘솔 상단의 "앱을 인증해야 합니다" 배너는 아래 브랜드 인증 얘기다.

**브랜드 인증**은 동의 화면에 "리틀핑거" 이름과 로고를 보여주기 위한 것이다. 안 해도 로그인은
되지만, 그동안 동의 화면에는 앱 이름 대신 `vepnrrmxvsytguocicfe.supabase.co`가 보여 신뢰가
떨어진다. 브랜딩 페이지 → **문제 보기**에 뜬 4개와 해결책:

| # | 콘솔 문구 | 해결 | 담당 |
|---|---|---|---|
| 1 | 홈페이지 URL(`https://littlefinger-app.web.app`)의 웹사이트가 나에게 등록되어 있지 않습니다 | Search Console에서 도메인 소유권 확인(아래 절차) | PO + 엔지니어 |
| 2 | 로그인 페이지가 홈페이지보다 먼저 표시됩니다 | `/`를 로그인 컨트롤 없는 공개 홈으로 교체 — 엔지니어가 배포 | 엔지니어 |
| 3 | 홈페이지에 앱의 목적에 관한 설명이 없습니다 | 같은 공개 홈에 목적·기능·원칙 설명 | 엔지니어 |
| 4 | 동의 화면 앱 이름(`Liitlefinger`)이 홈페이지의 앱 이름과 일치하지 않습니다 | 브랜딩 → **앱 이름**을 `리틀핑거`로 고치고 **저장** | PO |

**Search Console 소유권 확인 (문제 1)**

1. https://search.google.com/search-console 에 **task@deephigh.ai**(GCP 프로젝트
   `littlefinger-506104`의 소유 계정)로 로그인한다.
2. 속성 추가 → **URL 접두어** → `https://littlefinger-app.web.app/` → 계속.
3. 소유권 확인 방법에서 **HTML 파일**을 골라 `googleXXXX.html`을 내려받아 엔지니어에게 준다
   (HTML 태그 방식도 가능 — 그때는 `content` 값을 보낸다. 둘 다 비밀 아님).
4. 엔지니어가 파일을 `apps/web/public/`에 넣고 배포한다 — **2026-09-03 완료**:
   `https://littlefinger-app.web.app/googleb324b92c6f5d9c19.html` 이 원문 그대로 200으로
   응답하고, `apps/web/src/seo.test.ts`가 파일을 고정한다(지우면 소유권이 끊기므로). 이제
   Search Console에서 **확인**을 누른다 → "소유권이 확인됨".

**참고 (2026-09-03 두 번째 시도)** — 공개 홈을 배포한 뒤에도 문제 2·3이 그대로 남았다. Google의
자동 검사는 JavaScript를 실행하지 않고 HTML만 읽는데, 우리 웹은 React SPA라 첫 HTML 본문이
비어 있었기 때문이다. 이제 빌드가 홈 본문을 `index.html`에 정적으로 넣고(딥 경로는 빈
`app.html`), Search Console 소유권은 "인증된 소유자"로 확인됐다. 재검사부터는 세 문제 모두
해소된 상태로 검사된다.

**세 번째 시도 뒤(2026-09-03 15:20)** — 남은 것은 문제 1(소유권)과 2(로그인 페이지)뿐이었다.
확인한 사실: GCP IAM에서 task@deephigh.ai는 프로젝트 **소유자**이고 Search Console 소유권도
같은 계정으로 확인돼 있다. Search Console **실제 URL 테스트**는 홈을 정상 렌더링한다(영어 버전
제목·목적·기능, 리소스 전부 로드, 콘솔 오류 없음, 로그인 화면 없음). 즉 페이지는 요건을
충족하고, 남은 두 문구는 브랜드 검사기의 소유권 동기화 지연과 페이지 캐시로 보인다 — 같은
증상으로 며칠 걸린 사례가 Google 개발자 포럼에 여럿 있다. 그래서:

1. **몇 시간~하루 뒤** 다시 **문제를 해결함 → 계속**으로 재인증한다(그 사이 아무것도 바꾸지
   않는다).
2. 그래도 같으면 **발견된 문제가 잘못되었다고 생각됨 → 추가 검토 요청**을 고르고 이렇게 적는다:
   "`https://littlefinger-app.web.app/` 은 Search Console에서 프로젝트 소유자(task@deephigh.ai)
   계정으로 소유권이 확인되어 있고(HTML 파일 방식), 홈페이지는 로그인 없이 앱 이름·목적·기능을
   정적 HTML로 제공합니다. Search Console 실제 URL 테스트 결과 정상 렌더링됩니다." 수동 검토는
   2~3영업일이다.

**재인증 순서** — 위 1~4가 끝난 뒤: 브랜딩 페이지 → **문제 보기** → **문제를 해결함**(브랜딩
재인증 요청) → **계속**. 자동 검사는 보통 몇 분 안에 끝나고 인증 상태가 **게시 준비됨**으로
바뀐다 → **브랜딩 게시**. 다시 실패하면 문제 보기에서 **발견된 문제가 잘못되었다고 생각됨 →
추가 검토 요청**(수동 검토, 2~3영업일). 승인된 도메인의 `vepnrrmxvsytguocicfe.supabase.co`는
우리 소유가 아니라 Search Console 확인이 불가능하다 — 그 도메인이 문제로 뜨면 수동 검토
요청에 "Supabase Auth가 쓰는 서드파티 OAuth 리디렉션 도메인"이라고 적는다. 로고는 그대로
두어도 된다(인증 통과 뒤 동의 화면에 표시된다).

**확인** 대상 페이지 게시 상태 **프로덕션 단계**(완료). 브랜드 인증은 브랜딩 페이지 인증
상태가 **게시됨**이면 끝. 테스트 사용자 목록에 없는 Google 계정으로 기기에서 앱 로그인 1회는
지금 바로 가능하다.

## 5. 이메일 테스트 로그인 서버 제거 (PO 결정 2026-09-03)

공개 트랙은 누구나 설치한다. 서버에 켜져 있는 이메일 로그인은 `test@test.com`…`test10@test.com`
(비밀번호 = 이메일)로 anon 키만 있으면 누구나 로그인할 수 있는 상태다. 정본 절차는
`docs/setup/email-test-login-removal.md` §2.

**경로** supabase.com/dashboard → 프로젝트 `vepnrrmxvsytguocicfe`.

1. **Authentication → Sign In / Providers → Email** → *Enable Email provider* **OFF** → Save.
2. **Authentication → Users** → `test@test.com` … `test10@test.com` 10개 계정 **삭제**.
3. 같은 Providers 화면 상단의 *Allow users without an email* 은 **ON 유지**(카카오 이메일 미수집
   결정에 속한 설정, CLAUDE.md §6-1).
4. 절대 `supabase config push`를 쓰지 않는다(Dashboard만).

이후 개발 빌드와 로컬 웹의 "테스트 로그인" 버튼은 서버가 거절한다 — 앞으로 E2E는 Kakao/Google
실계정으로만 한다.

**확인** 엔지니어에게 "5번 완료"라고 알리면 §3 사후 확인(`grant_type=password` → 4xx)을 실행해
결과를 `docs/DEVELOPMENT_STATUS.md`에 적는다.

## 9. 공개 테스트 버전에 code 21 AAB 첨부

엔지니어가 `littlefinger-open-v0.2.0-code21.aab`와 SHA-256을 건넨 뒤 진행한다.

**경로** **테스트 및 출시 → 테스트 → 공개 테스트 → 출시** 탭 → "제목 없는 버전" → **버전 수정**.

1. **App Bundle → 업로드** → 파일 선택. 업로드가 끝나면 버전 코드 **21** 이 보인다.
2. **출시명**: `0.2.0 (21)` (자동 채움이면 그대로).
3. **출시 노트**: `<ko-KR>` 블록에 §5 한국어, `<en-US>` 블록에 §5 영어를 붙여 넣는다.
4. **다음** → 오류가 없어야 한다(경고 "난독화 매핑 파일 없음"은 무시 가능) → **저장**.
5. **버전 검토** → **공개 테스트로 출시 시작** — 첫 앱은 이 단계가 실제 게시가 아니라 "검토 대기
   묶음에 포함"이다. 실제 전송은 §10에서 한 번에 한다.

**확인** 공개 테스트 페이지의 진행 표시가 **버전 미리보기 및 확인 ✓** 로 바뀌고, 최신 버전
및 번들 화면에 공개 테스트 행이 `21 (0.2.0)`으로 보인다.
