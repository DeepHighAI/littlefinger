**문서 목적**: 상위기획서 오픈 이슈 **N-3(프레임워크 확정)** 의사결정
**대상 독자**: PO(대표) — 개발 지식 없이 의사결정
**전제 조건**: ① 안드로이드 앱 + 수락용 웹 병행(D3 확정) ② 카카오 로그인 단독 ③ 광고 수익 ④ **모든 기술스택은 무료 사용 가능한 것만** ⑤ 1인 개발 + AI 에이전트 코딩

## 1. 결론 (먼저 읽으세요)

**1순위 추천: React Native + Expo (TypeScript)**

이유는 세 줄로 요약됩니다. 첫째, 앱과 수락 웹을 **언어 하나(TypeScript)** 로 만들 수 있어 1인 개발자가 머릿속에 담아야 할 것이 절반입니다. 둘째, **AI 에이전트가 가장 잘 다루는 조합**입니다 — TypeScript는 현재 가장 널리 쓰이는 언어이고, Expo는 프로젝트를 만들 때 AI 에이전트용 지침 파일(`AGENTS.md`/`CLAUDE.md`)을 자동으로 넣어줍니다. 셋째, 나중에 **iOS를 추가할 때 코드를 다시 쓰지 않아도** 됩니다.

**단, 이 추천에는 하나의 명확한 약점이 있습니다.** 카카오 로그인을 붙일 때 쓰는 부품이 **카카오 공식이 아니라 개인 개발자가 만든 것**입니다. 리틀핑거는 카카오 로그인이 유일한 로그인 수단이므로, 이 부품이 방치되면 서비스 전체가 멈출 수 있는 구조입니다. (대응 방안은 5장에 정리)

### 순위와 판단

| 순위 | 안 | 한 줄 평가 | 이 안을 골라야 하는 경우 |
|---|---|---|---|
| **1** | **React Native + Expo** | 1인 개발·AI 코딩에 가장 유리, 카카오 부품만 비공식 | **속도와 유지보수 부담을 최우선**으로 볼 때 |
| 2 | Flutter | 카카오 공식 지원, 대신 언어를 2개 써야 함 | **"카카오 공식 지원"을 절대 조건**으로 볼 때 |
| 3 | Kotlin + Next.js | 안드로이드 품질은 최고, 대신 iOS를 처음부터 다시 만들어야 함 | **안드로이드 단일 플랫폼을 확정**하고 품질을 최우선할 때 |

> **결정을 뒤집는 단 하나의 질문**: "카카오 로그인 부품이 공식이 아니어도 감당할 수 있는가?"
> 감당 가능하면 **1순위(React Native)**, 감당 불가면 **2순위(Flutter)** 입니다. 3순위는 iOS를 영구히 포기할 때만 유효합니다.

> ⚠️ **기존 문서와 달라진 점**: 상위기획서 v1.1의 오픈 이슈 N-3에는 **"Flutter 우선 검토"** 로 적혀 있습니다. 이번 조사에서 ① 카카오 Flutter SDK가 **웹을 지원하지 않아** Flutter를 골라도 언어가 2개가 되는 점, ② AI 에이전트 도구 성숙도 격차가 확인되어 **추천 순위가 뒤바뀌었습니다.** 대표님이 ②안(Flutter)을 선택하셔도 기획 정합성에는 문제가 없습니다.

## 2. 먼저 정리해야 할 오해 — 실제 결정 범위는 생각보다 좁습니다

3개 안을 "앱+웹을 통째로 만드는 3가지 방법"으로 보면 비교가 어렵습니다. 조사 결과 **수락용 웹은 어떤 안을 골라도 TypeScript로 만들게 됩니다.** 근거는 두 가지입니다.

**근거 1 — Flutter Web은 수락 웹에 쓸 수 없습니다.** 상위기획서 §13은 수락 웹의 로딩 목표를 **3초 이내**로 정했고, 상대방은 대부분 카카오톡 인앱 브라우저로 들어옵니다. Flutter Web은 첫 화면을 띄우는 데만 압축 기준 **1.5~1.8MB**를 내려받아야 하고, Flutter 공식 문서 스스로 "마케팅·검색 노출용 정적 페이지에는 권장하지 않는다"고 안내합니다.

**근거 2 — 카카오 Flutter SDK는 웹을 지원하지 않습니다.** 카카오 공식 `kakao_flutter_sdk` 2.0.0+1의 지원 플랫폼은 **Android, iOS뿐**이고 웹은 "가까운 시일 내 지원 예정"으로만 적혀 있습니다. 즉 Flutter를 골라도 수락 웹의 카카오 로그인은 **JavaScript SDK**로 따로 만들어야 합니다.

**따라서 실제 결정 사항은 하나입니다: "안드로이드 앱을 어떤 언어로 만들 것인가."**

| 안 | 안드로이드 앱 | 수락용 웹 | 개발자가 다뤄야 하는 언어 |
|---|---|---|---|
| A. Flutter | Dart | TypeScript (별도) | **2개** |
| B. React Native + Expo | TypeScript | TypeScript | **1개** |
| C. Kotlin + Next.js | Kotlin | TypeScript | **2개** |

B안만 언어가 하나입니다. 다만 **"언어가 같다 = 코드를 그대로 재사용한다"는 아닙니다.** 앱 화면과 웹 화면은 부품이 다르기 때문에 화면 코드는 각각 써야 하고, 재사용되는 것은 데이터 형식 정의, 유효성 검사 규칙, 서버 통신 코드입니다. 이 정도만으로도 1인 개발에서는 큰 차이입니다.

## 4. 축별 상세 근거

### 4-1. 카카오 로그인 — B안의 유일한 약점 (가중치: 상)

카카오가 **직접 만들고 책임지는 SDK**는 Android, iOS, JavaScript, Flutter **4종**입니다. **React Native는 이 목록에 없습니다.**

| 안 | 사용할 부품 | 제작 주체 | 상태 |
|---|---|---|---|
| A. Flutter | `kakao_flutter_sdk` 2.0.0+1 | **카카오 공식**(인증 퍼블리셔 developers.kakao.com) | Android/iOS 지원, 웹 미지원 |
| B. RN | `@react-native-kakao/user` 2.4.6 | **개인 개발자**(GitHub: mym0404) | 활발히 관리 중, 최신 아키텍처 대응 |
| C. Kotlin | 카카오 Android SDK | **카카오 공식** | 가장 먼저 업데이트되는 1급 지원 |
| 공통(웹) | 카카오 JavaScript SDK | **카카오 공식** | 3안 모두 동일하게 사용 |

**이것이 왜 중요한가**: 리틀핑거는 MVP에서 카카오 로그인이 **유일한 로그인 수단**입니다. 로그인이 막히면 신규 가입과 상대방 수락이 모두 멈춥니다. B안은 이 지점의 부품이 회사가 아닌 **개인 1명에게 의존**합니다. 현재는 관리가 잘 되고 있지만(2.4.6이 최근 배포됨), 그 개인이 손을 놓으면 대체할 공식 경로가 없습니다.

**추가로 알아야 할 제약 (3안 공통)**:
- 카카오 JavaScript SDK v2는 **팝업 로그인이 제거**되어 **화면 이동(리다이렉트) 방식만** 가능합니다. 세부기능명세서는 이미 리다이렉트 방식으로 작성되어 있어 문제 없습니다.
- 구버전 JavaScript SDK(1.43.6 이하)는 **2026-12-31 지원 종료**입니다. 처음부터 v2로 시작해야 합니다.
- 카카오톡 인앱 브라우저에서는 `prompt=none` 옵션으로 **로그인 버튼을 누르지 않아도 자동 로그인**이 가능합니다. 상대방 진입장벽 최소화(원칙 P6)에 직접 도움이 되므로 세부기능명세서 F-01에 반영할 것을 권합니다.
- Expo를 쓸 경우 카카오 로그인은 **Expo Go(간편 실행 앱)에서 절대 작동하지 않습니다.** 처음부터 실제 앱을 빌드해 테스트해야 합니다 — 초반에 한 번 넘어야 할 문턱입니다.

### 4-2. 수락 웹 3초 달성 (가중치: 상)

2장에서 정리한 대로 3안 모두 수락 웹은 TypeScript로 만들며, 목표 달성이 가능합니다. 차이는 "앱 코드와 얼마나 이어지는가"입니다.

- **A안**: Flutter 앱과 웹이 완전히 분리됩니다. 데이터 형식이 바뀌면 Dart와 TypeScript **양쪽을 손으로 맞춰야** 하고, 여기서 어긋나면 찾기 어려운 버그가 됩니다.
- **B안**: 앱과 웹이 같은 언어이므로 데이터 형식·검증 규칙·서버 통신 코드를 공유합니다. 화면까지 공유하려면 `react-native-web`(Expo SDK 57에 0.21 포함, 용량 30~40KB 추가)을 쓸 수 있지만, **화면 크기별 대응·상단 고정 요소·마우스 올림 효과가 지원되지 않는 제약**이 있습니다. 수락 웹은 6개 화면짜리 단순 흐름이므로 **화면은 별도로, 로직만 공유**하는 방식을 권합니다.
- **C안**: Next.js 16.2.11로 웹만 보면 가장 최적입니다. 대신 Kotlin ↔ TypeScript 간 데이터 형식 동기화 문제는 A안과 동일합니다.

### 4-3. 1인 유지보수 부담 (가중치: 상)

언어가 2개면 실제로 늘어나는 일은 언어 학습이 아니라 **관리 대상의 중복**입니다: 오류 메시지 읽는 방식 2종, 부품 설치 방식 2종(pub.dev/Gradle vs npm), 업데이트 주기 2종, 그리고 위에서 말한 **데이터 형식 수동 동기화**입니다. 개발 지식이 없는 상태에서 문제가 생겼을 때 "어느 쪽 문제인지" 판단하기 어려운 것이 가장 큰 부담입니다.

C안은 여기에 **Android 빌드 도구(Gradle)** 부담이 추가됩니다. Gradle은 버전 충돌 오류가 자주 발생하고 오류 메시지가 난해해서, 개발 지식이 없으면 AI 에이전트가 못 고칠 때 직접 개입할 여지가 거의 없습니다. 3안 중 C안이 이 위험이 가장 큽니다.

### 4-4. AI 에이전트 궁합 — 바이브코딩의 핵심 (가중치: 상)

대표님의 개발 방식이 AI 에이전트 코딩이므로, 이 축은 실질적으로 **성공 확률**과 직결됩니다.

| 항목 | A. Flutter/Dart | B. RN/TypeScript | C. Kotlin |
|---|---|---|---|
| 언어 사용 규모(참고 지표) | Dart 5.9% | **TypeScript 43.6%** | Kotlin 10.8% |
| AI가 학습한 코드량 | 보통 | **가장 많음** | 보통 |
| AI 에이전트 전용 지원 | 도구 있음 | **프로젝트 생성 시 AI 지침 파일 자동 포함 + 공식 Claude Code 플러그인** | 사실상 없음 |
| 평가 | ★★★★ | **★★★★★** | ★★ |

핵심은 마지막 줄입니다. Expo로 프로젝트를 만들면 AI 에이전트용 지침 파일(`AGENTS.md`, `CLAUDE.md`)이 **자동 생성**되고 공식 Expo Claude Code 플러그인이 함께 켜집니다. 다른 두 안은 이 지침을 사람이 직접 써야 합니다. 대표님의 작업 방식에 정확히 맞춰진 조합은 B안뿐입니다.

> **주의**: 위 % 수치는 개발자 설문 응답 비율로, "AI가 이 언어를 얼마나 정확히 쓰는가"를 직접 측정한 값이 **아닙니다.** 학습 데이터량의 간접 지표로만 해석해야 합니다. (8장 참조)

### 4-5. 광고(AdMob) 연동 (가중치: 중)

3안 모두 가능합니다. A안은 구글 공식 Flutter 플러그인, C안은 구글 공식 Android SDK로 가장 확실합니다. B안은 `react-native-google-mobile-ads` 16.3.3을 쓰는데, 제작사가 **Invertase**(React Native용 Firebase 공식 라이브러리를 만드는 조직)여서 4-1의 카카오 부품과 달리 **개인 의존 위험은 없습니다.**

참고로 광고는 세부기능명세서에서 `ads_enabled` 서버 설정으로 꺼둔 상태로 출발하고, 일 확정 100건 도달 시 대표님이 직접 켜는 구조입니다. 즉 광고 연동은 MVP 초기의 위험 요소가 아닙니다.

### 4-6. iOS 확장 (오픈 이슈 N-2) (가중치: 중)

현재 iOS 시점은 미결정입니다. 그런데 구조상 **아이폰 사용자도 결국 앱이 필요합니다** — 초대받은 사람은 웹으로 해결되지만, 아이폰 사용자가 **직접 약속을 만들려면** 앱이 있어야 합니다.

- **A·B안**: 같은 코드로 iOS 앱을 낼 수 있습니다. 추가 작업은 화면 점검과 심사 대응 수준입니다.
- **C안**: Kotlin으로 만든 Android 앱은 iOS에서 쓸 수 없습니다. **Swift로 앱 전체를 다시 만들어야 합니다.** 코틀린 멀티플랫폼(KMP)이라는 우회로가 있지만, 화면을 공유하는 부분(Compose Multiplatform)은 웹에서 아직 **베타** 단계여서 지금 의존할 수 없습니다.

C안을 3순위로 둔 결정적 이유가 이것입니다.

### 4-7. 장기 운영 리스크 (가중치: 중)

| 안 | 현재 상태 | 리스크 |
|---|---|---|
| A. Flutter | Flutter 3.44 / Dart 3.10, 분기별 정기 배포 유지 | 구글의 투자 기조가 **"확장 → 유지"로 이동**, 담당 인력 약 50명 수준. 당장 문제는 없으나 신기능 속도 저하 가능 |

| C. Kotlin | 2026-05-19 구글이 **"Compose First"** 선언, 구버전 방식은 유지보수 모드 | 프레임워크 리스크는 3안 중 가장 낮음 |

## 5. 각 안의 최대 리스크와 대응책

| 안 | 최대 리스크 | 대응책 | 대응 난이도 |
|---|---|---|---|
| **B (추천)** | 카카오 로그인 부품이 **개인 제작** → 방치 시 로그인 전체 중단 | **카카오 공식 REST API 기반 로그인으로 전환.** 앱 안에서 브라우저 창을 띄워 카카오 공식 로그인 페이지로 보내는 방식(`expo-auth-session`)으로, 개인 제작 부품 없이 **카카오 공식 서버만** 사용합니다. 대신 "카카오톡 앱으로 바로 로그인"의 매끄러움이 일부 줄어듭니다 | **낮음** — 우회로가 명확히 존재 |
| **A** | 언어 2개로 인한 데이터 형식 불일치 버그 | 서버 API 규격 문서를 단일 기준으로 두고 양쪽을 그에 맞춤(세부기능명세서 §5·§6이 이 역할) | 중간 — 지속적 주의 필요 |
| **C** | iOS 진출 시 앱 전체 재작성 | 없음. **iOS를 포기하거나 비용을 다시 지불**하는 선택뿐 | **높음** — 구조적 문제 |

> B안의 리스크는 **"우회로가 있는 리스크"** 이고, C안의 리스크는 **"우회로가 없는 리스크"** 입니다. 이 성격 차이가 순위를 갈랐습니다.
